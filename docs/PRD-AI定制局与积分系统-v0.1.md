## 1. 产品目标

玩家通过十二关普通局学习构筑并积累定制积分。获得资格后，在开局回答“这次你想整什么玩法？”，AI 将想法转成一套游戏能够执行的主题规则，玩家预览并确认后开始十二关定制局。

希望玩家因为主题改变选牌、弃牌和购买决策，并在中后期形成自己的强力组合。允许后期出现爆炸分数；避免开局无条件获得巨大倍率，让后续选择失去意义。

普通局本身应当值得游玩，积分不能成为迫使玩家反复完成无聊流程的门槛。定制效果也不能仅有名称和文案变化。

## 2. 当前项目基线

本节为已经存在的实现。发生冲突时以本次查阅的代码为准，不能沿用早期六关文档中的数值。

| 模块 | 当前能力 |
| --- | --- |
| 对局 | 四幕十二关；每关4次出牌、3次弃牌；8张手牌；每次选1～5张 |
| 牌组 | 每关重新生成、洗混52张牌；没有跨关永久改造扑克牌的状态 |
| 计分 | 九种牌型；所有打出的牌计入基础筹码；Joker按顺序结算 |

| 经济 | 初始5金币；通关基础奖励为5＋剩余出牌次数；部分Joker另有经济效果；刷新花费2金币 |

| 辅助 | 图鉴、当前手牌最优出牌枚举、按稀有度和价格计算的购买建议 |
| 表现 | GSAP计分动画；音乐音效；音量、动画和计分显示设置 |
| 持久化 | 现有localStorage仅保存设置；刷新会重新开局；没有跨局积分账本 |
| 模型与服务 | 当前“AI出牌”是本地组合搜索，不调用语言模型；项目没有定制生成后端 |
| 部署 | Vue 3＋Vite＋Bun；main推送触发GitHub Actions构建并发布GitHub Pages |

## 3. 目标用户与核心场景

- 新玩家：通过普通局理解筹码、倍率和组合；首次免费体验定制；失败仍看到积累进展。
- 已能形成构筑的玩家：通过完整通关稳定获得定制机会，尝试不同主题。
- 喜欢表达和玩梗的玩家：输入人物、心情或一句话，得到可理解、可执行的玩法，不必编写规则。

核心场景示例：玩家普通局通过第8关后失败，获得3积分；与此前3分合计达到6分；进入定制页，输入“这次想当越穷越强的赌徒”；生成预览展示低金币加成与初始牌；确认后扣6分，开始定制局。

## 5. 用户流程与页面

### 5.1 主入口（新增）

展示“普通局”“定制局”“继续游戏”和定制积分余额。首次展示“免费体验1次”；免费机会使用后，展示“定制积分 4/6”及简短获取说明。

积分不足时可以查看玩法介绍，不能提交收费生成请求。已有未结束对局时优先提供继续；新开局必须明确放弃旧局的影响，不能静默覆盖。

### 5.2 普通局

保持当前十二关流程。胜负结算页新增本局已通过关数、获得积分、累计积分及“再来一局/前往定制”。到达奖励里程碑可轻提示预计奖励，实际入账只发生在对局结束时。

### 5.3 定制生成与预览（新增）

1. 标题“这次你想整什么玩法？”，提供少量示例与“随机给我一个”；不要求玩家填写复杂表单。
2. 提交后展示生成状态、取消入口；同一请求不能重复发送。
3. 预览展示主题名称、核心规则、初始牌效果、必要的触发条件与上限、入场消耗。
4. 玩家可以确认开局或返回修改；修改后重新生成计入独立的生成配额。
5. 点击确认后，系统校验资格、扣除积分或首次免费机会、保存新对局，再进入第1关。

候选输入上限200个字符；超过时保留原文并要求缩短，不静默截断。长度与生成配额均为可配置参数。

### 5.4 定制对局与结算

开局和侧栏明确标识“定制局”，随时可查看核心规则。卡牌预览、实际得分和动画使用同一套执行逻辑。通过第12关或失败后展示主题和战绩；默认不发定制积分，防止定制局自循环刷资格。

第一幕（1～3关）理解主题，第二幕（4～6关）建立配合，第三幕（7～9关）调整成型，第四幕（10～12关）兑现构筑。允许个别强力组合提早形成，不承诺每局严格符合此节奏。

### 5.5 摧毁与本局牌库更新（已确认，尚未实现）

目的：让玩家在填满槽位后继续调整组合，并通过牺牲金币回收收益缩小后续候选池。这里移除的是本局Joker候选，不改变52张扑克牌，不删除全局37张定义或图鉴。

| 操作 | 金币 | 腾出槽位 | 后续商店候选 |
| --- | --- | --- | --- |
| 出售，现有功能 | 原价一半向下取整且至少1金币 | 是 | 不封禁，刷新或未来商店仍可能出现；当前货架的已售标记不因出售重置 |
| 摧毁，新增功能 | 不返还；第一版不另收费 | 是 | 该牌ID本局永久排除，重开恢复 |

规则：

1. 只能在商店操作已拥有的基础Joker，不能直接清除未购买的货架商品或图鉴中的卡。
2. 每次进入一个新的关间商店，最多成功摧毁1张；付费刷新、关闭界面、刷新网页及恢复存档均不重置次数。进入下一关后的下一家商店才重置。
3. 成功后同时移除持有实例及成长进度，将牌ID写入本局移除集合，并消耗本店次数。取消确认不改变任何状态；重复提交不能产生第二次效果。
4. 未来首次进店和刷新选牌均过滤该集合，不能因候选不足而把摧毁牌补回。重新开局清空集合，恢复完整基础牌库。
5. 摧毁不主动刷新当前货架，不赠送新牌，不改变金币、创造点或定制积分；要换商品仍使用正常刷新。
6. 沿用现有类别权重：类别抽空后，剩余非零权重类别按相对比例重分配；零权重类别不解锁。合格候选不足3张时只展示剩余候选，禁止重复填满。
7. 普通局和定制局中的基础Joker遵循同一规则。生成初始牌及未来自创牌的摧毁范围另议，不能据此默认扩展。

交互：在“我的组合”牌下并列展示出售与摧毁，文案清楚区分收益。摧毁需确认，示例为“摧毁「绿色小丑」？不返还金币，已积累成长将清除，本局不会再出现，下一局恢复。”商店展示“本店摧毁机会 1/1”以及“本局已移除 X 张”，支持查看名单；图鉴保留全部定义，可标识本局已移除状态。

风险：购买便宜牌后摧毁可提高剩余牌的集中度；清空普通类别还会间接提高稀有类别概率。次数限制只是第一版约束，需记录每局摧毁次数、成本、剩余候选与稀有度分布。先验证该机制，再决定普通槽扩容幅度；不同时把37张牌库的容量假设改掉。

## 6. 定制积分与入场规则

### 6.1 奖励表（原型候选值）

| 普通局最高通过关数 | 结束时奖励 |
| --- | ---: |
| 0 | 0 |
| 1～3 | 1 |
| 4～6 | 2 |
| 7～9 | 3 |
| 10～11 | 4 |
| 12，完整通关 | 6 |

按最终档位结算一次，不逐档累加；分数溢出不额外增加积分。“最高通过关数”不等于正在挑战的关卡编号：第7关失败代表已通过6关，应奖励2分。

### 6.2 消耗与结算

- 定制入场6分；每个玩家首次免费1次。余额默认不设过期；积分不能转换为金币。
- 首次免费机会只在确认开局成功时消耗；生成失败、预览取消不消耗。
- 普通局自然失败或通关正常结算；暂停/关闭保存进度，不结算。MVP建议明确放弃或重开不发积分，避免通过退出按钮快速刷奖。
- 定制局开始后，正常失败或主动放弃不退款；仅因系统故障无法恢复的对局允许幂等补偿，需关联原扣费记录。
- 每个runId最多一笔通关/失败奖励，每次开局最多一笔扣费；连点、重试、刷新和多标签页不能重复入账或扣款。
- 若同一账号存在未结束定制局，优先恢复，MVP不支持并行开启多个付费定制局。

### 6.3 刷分与节奏验证

不能仅依赖“未过第一关不给分”。需比较主动早败策略与正常推进的积分/分钟，并记录每档真实用时。若早败明显更划算，优先调整早期奖励和后期收益，再决定是否需要每日奖励限制；本稿不承诺已解决刷分。

免费生成与游戏积分是两套限制。候选内测配额为每位玩家每日3次有效生成尝试、同时最多1个请求；基础输入检查不计次数，用户主动换结果计次数，服务错误不计玩家配额但仍计服务成本。配额可调整，不把“预览不扣分”解释为无限免费生成。

## 7. AI职责与可执行玩法

### 7.1 生成边界

AI负责解释输入、选择受支持机制并生成简短主题文案；程序负责参数预算、校验、保存和执行。正常生成只调用一次模型，不自动追加解释、审核、联网搜索或循环重写。

输出“主题＋一条核心规则＋一张初始牌”。本期建议初始牌占用普通5槽中的1槽，可按普通规则出售，售出不移除本局核心规则；它不构成此前讨论的独立创造区。此项属于待评审的MVP取舍。

核心规则作为独立本局配置保存，不占卡槽。初期只允许一条，避免多个新增规则互相放大后难以理解。

### 7.2 首批执行机制建议

| 类型 | 可用条件或效果 | 实现说明 |
| --- | --- | --- |
| 计分条件 | 出牌张数、牌型、花色/点数数量、金币档位、剩余手数/弃牌数 | 复用现有上下文；新增条件组合须白名单化 |
| 计分效果 | 加筹码、加倍率、条件乘倍率 | 值由统一预算限制；禁止任意公式字符串 |
| 成长 | 出牌/弃牌触发的有上限累计 | 只在提交动作时推进；预览不修改状态 |
| 经济 | 过关奖励修正、弃牌奖励 | 明确事件与单次上限，不能触发自身无限循环 |

低金币玩法示例：核心规则在金币低于阈值时提供有限加成，初始牌帮助相关打法。阈值、加成与配套牌具体值由预算配置和试玩确定；不能直接把文案示例当作已定数值。

暂不支持回退时间、跨关改造52张牌组、任意复制触发或新增游戏世界。需要这些能力时先扩展引擎及测试，再允许模型选择。

### 7.3 执行一致性

明确核心规则的结算阶段，MVP建议在基础牌型与牌面筹码之后、Joker从左至右结算之前应用；所有预览、动画、实际计分和最优出牌枚举必须一致。

结构化配置至少包含规则版本、触发条件、效果类型、参数与上限。不得执行模型输出的JavaScript，不使用eval；当前按固定Joker ID查找effect函数的方式需要扩展受控解释器，直接新增任意ID目前不会生效。

### 7.4 陌生梗、模糊输入与超纲

| 输入 | 产品行为 |
| --- | --- |
| 明确且受支持的玩法 | 尽量忠实实现，在预览中写清实际效果 |
| 普通人名、陌生梗 | 可作命名/主题灵感，不编造人物背景，也不声称准确理解出处；允许用户自行补充解释 |
| 只有情绪或模糊短语 | 在支持的机制中自由创作；不用默认多轮追问 |
| 明确要求未支持的能力 | 返回简短说明及一个可编辑的替代方向，不自动声称已实现，不扣入场积分 |
| 空内容或超长输入 | 本地校验，不调用模型 |

不建设单独“AI认识不认识这个梗”的审核模型。关键词创意表可后续添加，仅传递命中的少量条目。

## 8. 存档、账本与可靠性

当前刷新重新开局的行为必须在付费资格上线前解决。存档需覆盖普通局和定制局。

| 对象 | 必要内容 |
| --- | --- |
| 玩家资料 | playerId、积分余额、首次免费已用标记、资料版本 |
| 积分账本 | transactionId、runId、入账/扣费/补偿类型、数额、时间；唯一键防重复 |
| 生成草案 | draftId、原始输入、已校验配置、生成状态、机制/预算/模型版本 |
| 对局存档 | runId、模式、状态、最高通过关数、当前关卡、手牌及牌堆顺序、金币、手数/弃牌数、累计分、Joker顺序及成长、商店/已售状态、核心规则、配置版本 |
| 可复现随机 | seed及生成器状态；需把现有Math.random改为可恢复随机来源，或完整保存下一次随机所需状态 |
| 本局摧毁状态 | destroyedJokerIds、本店是否已摧毁及对应关间商店标识；与持有牌移除同步保存，重开清零 |

在出牌、弃牌、购买、出售、摧毁、调序、刷新、关卡切换和结算这些动作提交后保存。动作已经提交但动画未播完时刷新，恢复提交后的逻辑状态，不重复计分、成长或发奖。

确认定制开局时，消费资格与创建存档须作为一次不可分割的操作处理。请求结果不明时先查询原请求状态，不能重新扣款。

个人设备原型可以先使用本地存储验证流程，但它不是可靠的防作弊边界。面向其他玩家发放资格与生成额度前，应建立服务端身份、账本和进度校验；不可直接相信前端提交的“通过了12关”。最小可信方案可用服务端种子和动作记录验证结果，具体工程选型待定。

存档损坏时提示恢复或重新开始，不静默删除积分；旧版本配置需兼容或明确迁移。模型/规则升级不能悄悄改变正在进行的定制局。

## 9. 模型接入、成本与异常

采用“网页 → 游戏后端 → 自部署开源模型 → 配置校验 → 返回草案”。玩家无需配置API Key。模型与运行硬件尚未选定；本地部署有硬件、内存、电力和并发成本，不能视为无限免费。

前端可以继续用GitHub Pages，动态服务另行部署。模型服务位于后端之后，不直接把未经鉴权的推理端口暴露给玩家。普通局的开始和本地游玩不应依赖模型在线。

模型请求只带玩家本次输入、受支持机制摘要和预算约束，不携带完整聊天记录。输出限制为一个结构化草案；请求长度、输出上限、超时和并发额度可配置。模型返回非法配置时拒绝草案，不自动反复调用。

| 异常 | 用户结果 |
| --- | --- |
| 模型离线、超时或队列满 | 显示原因，可返回普通局；不扣积分或免费机会 |
| 非法/不受支持配置 | 不进入游戏，保留输入；提示重新描述或稍后重试 |
| 预览期间余额发生变化 | 确认时重新校验；不足则保留草案，不创建对局 |
| 重复确认/网络重试 | 返回同一runId及相同扣费结果 |
| 已扣费但页面关闭 | 下次从已创建的存档继续 |
| 玩家取消请求 | 不进入对局、不扣资格；迟到结果不能自动开始游戏 |

原型建议60秒请求超时、每玩家1个并发请求，实际体验目标以硬件测试为准。不得把未经测量的响应时间写成对外承诺。

## 10. 验收标准

以下为目标版本验收要求，尚未执行；现有规则测试通过不能替代新增功能验收。

| 编号 | 场景 | 通过标准 |
| --- | --- | --- |
| AC-01 | 普通局模式 | 现有十二关、37张牌、出售、调序、成长与商店逻辑保持可用 |
| AC-02 | 奖励边界 | 通过0/1/3/4/6/7/9/10/11/12关分别得到0/1/1/2/2/3/3/4/4/6分 |
| AC-03 | 去重结算 | 同一runId重复回调、刷新或多标签页只奖励一次 |
| AC-04 | 首次免费 | 取消和生成失败保留免费机会；首次成功开局仅消耗一次机会且不扣积分 |
| AC-05 | 收费开局 | 5分无法开局；6分成功后余额0；重复确认不重复扣费 |
| AC-06 | 模型异常 | 超时、非法JSON、越界数值、未知机制均不能进入对局或消耗入场资格 |
| AC-07 | 玩法差异 | 至少3种主题能够形成不同选择，例如少出牌、保留弃牌、低金币；实测记录而非只比较文案 |
| AC-08 | 计分一致 | 同一局面下预览、实际得分、动画结果与AI枚举一致；预览不推进成长 |
| AC-09 | 存档恢复 | 普通/定制局在出牌、商店及动画途中刷新后恢复，不重复扣费、计分或领奖 |
| AC-10 | 定制结算 | 胜负均不产出定制积分；主动放弃不退款；系统补偿最多一次 |
| AC-11 | 成本边界 | 正常成功生成只发起1次模型请求；取消、连点与换结果遵守独立配额 |
| AC-12 | 公开内测 | 不能仅通过修改前端余额绕过服务端生成资格；基础限流与预算熔断生效 |
| AC-13 | 摧毁与出售 | 摧毁不返金币，移除持有牌及成长并腾槽；出售仍返半价且不加入永久排除集合 |
| AC-14 | 本局候选过滤 | 摧毁牌在所有后续商店及刷新中均不出现；重开后恢复候选资格，图鉴定义不减少 |
| AC-15 | 摧毁次数 | 同店仅成功一次，取消不消耗，刷新/重载/恢复不重置；下一家店恢复一次 |
| AC-16 | 候选耗尽 | 类别耗尽遵循非零权重重分配；零权重不解锁；不足3张时不重复、不补回已摧毁牌 |
| AC-17 | 摧毁原子性 | 连点、重复请求或恢复存档不重复处理；持有牌、成长、排除集合与次数状态一致 |

保留并运行现有 `bun run test`、`bun run build`；扩展 `bun run balance:check`覆盖定制配置。现有平衡脚本只测试给定成型阵容，不能当作真人胜率或完整十二关经济模拟。

## 11. 观察指标与上线判断

| 要回答的问题 | 指标 |
| --- | --- |
| 资格是否太难获得 | 每次定制所需普通局数量、有效游玩时长及首次可用资格时间 |
| 是否鼓励刷早败 | 不同进度档位积分/分钟、早期主动送败比例；与正常推进对照 |
| 生成是否值得等待 | 合法草案率、确认开局率、重生成率、取消率、生成耗时P50/P95 |
| 主题是否改变玩法 | 牌型/出牌张数/弃牌/消费习惯变化，加上试玩访谈 |
| 爽感出现是否合适 | 分关失败率、单手过关比例、得分/目标比、通关率，与普通局分组比较 |
| 服务是否可承担 | 每次调用输入输出token、推理时长、每日请求量与峰值并发 |
| 清池是否过强 | 每局摧毁数量、购入后立即摧毁比例、金币成本、各类别剩余候选、目标组件获取时点 |

不先编造留存率或通关率目标。先做小规模试玩获得基线，再决定入场成本和生成预算。若普通局被普遍认为只是赚门票的负担，应降低门槛或调整模式关系。

## 12. 开发顺序与待决策项

本节是后续统一实施的顺序建议，当前仅更新需求，不开始编码。基础玩法的摧毁机制先单独验证，再决定关卡曲线与普通槽扩容是否组合上线。

1. **玩法原型**：手写3份结构化定制配置，接通规则执行、初始牌和十二关；验证主题是否有不同决策。
2. **资格与恢复**：模式入口、积分、首次免费、账本去重和完整存档；覆盖失败、刷新与多标签页场景。
3. **模型接入**：在同一接口下接自部署模型，加入配额、校验和失败处理；用真实输入测试成本与质量。
4. **小规模内测**：真人完整十二关试玩，测刷分效率、强度曲线、生成延迟；调整配置后再公开。

实现前/内测前需评审：6分入场与奖励档位；首次免费；初始牌占用普通槽及可出售规则；核心规则结算阶段；每日生成额度；部署硬件与模型；本地原型和公开版身份边界。

### 12.1 后续创造系统的约束保留

若恢复局中造牌方案：创造点通过通关获得，用于制造或强化；金币用于购买独立创造区的容量上限；普通5槽与创造槽分开。十二关3～4个创造槽仅为设想，未确定起始数量、上限、价格。回收、替换、强化、跨局收藏和与开局定制的组合均需另行设计，不能在本期默认实现。

### 12.2 普通关卡与普通槽扩容提案（待讨论，不作为实施定值）

用户反馈五张牌成型后可能很早覆盖终局11000分，希望后半程仍有更新组合的需求。现有固定阵容脚本显示不同流派差异较大，因此不能只按最强阵容上调所有门槛。

| 提案 | 讨论中的候选方案 | 决策状态 |
| --- | --- | --- |
| 目标曲线 | 第1～12关：250、400、650、1000、1600、2500、4000、6000、9000、13000、18000、25000 | 与扩容配套的测试设想，未确认 |
| 普通槽扩容 | 初始5槽，第6关后可购买第6槽，第9关后可购买第7槽，价格递增 | 解锁节点、价格和最终槽数均未确认；不同于自创槽 |
| 满槽换购 | 购买时选择旧牌出售，展示返还和净支出后确认完成交易 | 交互提案，未确认 |

确认过的摧毁规则见第5.5节。暂不增加其他献祭收益；先观察37张牌库在本局移除机制下的变化，再评估扩槽。调高分数、扩大容量和永久清池各自都会改变构筑，不应把三项假设一次定死。
